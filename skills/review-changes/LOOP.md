# Цикл ревью и исправлений

Правила для implement при выполнении отдельной задачи или плана. Самостоятельный запрос на review-changes остаётся проверкой без правок. Исправления выполняй только в рамках поручения на реализацию.

## Небольшая правка

Для небольшой правки по условиям [review-changes](SKILL.md) выполни один общий проход по всему согласованному объёму. Исправь подтверждённые замечания и проверь исправления, затронутое поведение и вызовы. Постоянные ID и формальный бюджет раундов не нужны. Заверши, когда существенные замечания устранены или обоснованно отклонены, а исправления проверены; необязательные улучшения сами по себе не требуют продолжения.

При новых существенных последствиях или неразрешённом споре перейди к полному режиму с имеющимися замечаниями и результатами проверок. Расширяй проверку по новым последствиям, указывая причину; уже проверенное без оснований не повторяй.

## Полный режим: раунды и замечания

Один раунд — все применимые проходы review-changes на одном снимке, независимо от числа исполнителей. По умолчанию бюджет — три раунда на задачу, включая первый. Для безопасности, прав доступа, потери данных или конкурентного изменения состояния можно продлить до пяти, если остаётся подтверждённый существенный дефект. Другой бюджет может задать пользователь. Повторный запуск после исправления не обнуляет счётчик.

Веди единый список замечаний: постоянный ID, источник, серьёзность, место, доказательство, решение и состояние. Решение — исправить или отклонить с причиной; состояние — открыто, ожидает проверки исправления, закрыто. Объединяя дубли, сохрани соответствие исходным ID. Необязательные улучшения отмечай отдельно; редкость сценария сама по себе не снижает серьёзность уязвимости или потери данных. Список можно вести в контексте, отдельный файл не обязателен.

## Действия implement в полном режиме

1. До первого раунда исправь уже известные ошибки в объёме задачи и выполни подходящие проверки. Передай ревьюеру цель, исключения, снимок по CHANGES.md, результаты проверок и ограничения.
2. Проверь каждое замечание по коду или воспроизведению. Исправляй подтверждённые дефекты в объёме задачи; отклонение обоснуй ссылкой на код, требование или результат проверки. Необязательное улучшение не требует исправления ради одобрения. Во время ревью сохраняй переданный снимок неизменным.
3. После исправлений повтори затронутые проверки. В следующий раунд передай прежнюю базу сравнения, новый снимок, список замечаний с решениями и изменения после предыдущего раунда. Обновление снимка не меняет исходный объём задачи.
4. Заверши цикл, когда нет ни открытых существенных замечаний, ни непроверенных исправлений поведения, а последнее ревью покрывает текущее поведение. Одни необязательные улучшения не требуют нового раунда. Правки только оформления, комментариев или документации не требуют нового раунда, если не меняют проверяемый контракт; проверь их непосредственно.

При существенном разногласии между исполнителем и ревьюером можно один раз привлечь независимого консультанта по правилам выбора модели в AGENTS.md. Передай конкретное замечание, снимок кода, требования, результаты проверок и аргументы обеих сторон. Консультант разбирает только спор без правок и своих субагентов; полный аудит заново не запускается. Проверь его аргументы по доказательствам. Консультация расходует один раунд общего бюджета и не обнуляет счётчик обменов аргументами; после исчерпания бюджета её не запускай.

Если бюджет исчерпан, а условия завершения не выполнены, или спор остаётся после двух обменов аргументами по одному замечанию, останови цикл и покажи пользователю доказательства сторон и оставшийся вопрос. Лимит, сбой или отсутствие ответа ревьюера не означают одобрение. Сообщи число раундов, проверенный снимок, подтверждённые исправления, причины отклонений и ограничения в общем отчёте задачи.

## Повторная проверка

Первый раунд покрывает весь согласованный объём. Последующие проверяют открытые замечания, исправления и затронутые ими вызовы и требования. Для каждого прежнего ID укажи: исправлено, остаётся или отклонение обосновано. Закрытое замечание возвращай только при регрессии или новых доказательствах; новый дефект получает новый ID. Расширяй проверку при изменении интерфейса или обнаруженной зависимости, с указанием причины, а не повторяй весь аудит автоматически.
