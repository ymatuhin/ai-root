# Реализация задачи

Для плана из нескольких задач прочитай [PLAN.md](PLAN.md): он задаёт порядок выполнения и интеграции. Для одиночной задачи выполни шаги ниже напрямую.

1. **Контекст и границы.** Используй уже собранные в разговоре факты, дочитывая код и правила проекта по пробелам. Зафиксируй критерии приёмки и исходное состояние рабочей папки (`git status`): сохрани чужие изменения и не включай их в свои исправления. Номер задачи используй из доступного источника; локальный текст достаточен без трекера.
2. **Реализация и проверка имён.** Внеси минимальное достаточное изменение. Подключай предметные правила по ситуации; при написании или правке тестов соблюдай критерии и границы моков из [tdd/tests.md](../tdd/tests.md) и [tdd/mocking.md](../tdd/mocking.md), а полный цикл [tdd](../tdd/SKILL.md) используй при работе test-first. Используй согласованные границы тестирования без повторного запроса. Если изменение ввело или переименовало функции, типы, переменные, поля или события, перепроверь новые имена по [good-naming](../good-naming/SKILL.md) и исправь дефектные.
3. **Проверки.** Выполни подходящие проверки затронутого поведения и обязательные проверки проекта.
4. **Ревью по уровню риска:**
   - **Быстрый путь (небольшая локальная правка без изменения контрактов, безопасности, сохранности данных и конкурентности):** сверь свой diff напрямую в контексте — нет ли ошибок и пропущенных граничных случаев, нарушений правил проекта, пропусков требований задачи, лишней сложности, а в тестах — тавтологий, проверок вызовов моков/деталей реализации и дублей между слоями; при правках повтори затронутые проверки. Читать `review-changes`, `CHANGES.md`, `LOOP.md` и `REPORT.md` не нужно.
   - **Полный путь (безопасность, данные, конкурентность, контракты нескольких модулей, неясные последствия или общий итог плана):** выполни [review-changes](../review-changes/SKILL.md) и цикл исправлений по [LOOP.md](../review-changes/LOOP.md), передав границу своего поручения и список исходно грязных посторонних файлов. Для отдельной части плана до интеграции достаточно локальных проверок.
5. **Отчёт.** На быстром пути кратко сообщи решённую проблему и эффект, затронутые файлы, статус выполненных проверок и ограничения. На полном пути или при запросе описания PR заверши по [REPORT.md](REPORT.md). Для отдельной части плана верни изменённые файлы, результат, проверки и ограничения для общего отчёта.

Готово, когда критерии приёмки выполнены, проверки и ревью выбранного уровня закрыты, а отчёт соответствует фактическому diff. Существенное изменение согласованных поведения, объёма или интерфейсов верни на согласование; обычные детали реализации решай сам.
