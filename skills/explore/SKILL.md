# Выбор подхода

Если неясна цель пользователя, задай один вопрос и жди ответа; факты о коде и окружении собирай сам.

1. Определи цель, ограничения и уже известные факты. Недостающие факты проверь по первоисточникам (код проекта, официальная документация, спецификации; независимые вопросы можно поручить параллельным read-only субагентам). Если исследование нужно сохранить отдельно и в проекте нет своей папки для заметок, запиши выводы с источниками в `.scratch/<тема>/research.md`.
2. Если разумный подход один — кратко обоснуй его найденными фактами. Если есть разные по сути подходы (где живёт логика, что берём готовым, какую часть задачи закрываем), сравни их в таблице с опорой на код и документацию:
   - первый — «Ничего не делать» (что останется плохим, у кого и как часто);
   - второй — самый простой вариант, закрывающий основные случаи;
   - далее — только варианты, которые ты сам рекомендовал бы при конкретных условиях.

   | Подход | Суть | Что покрывает | Цена | Главный риск |
   | ------ | ---- | ------------- | ---- | ------------ |
   | Ничего не делать | | | | |

3. Если рекомендуемый подход вводит новые зависимости, абстракции или этапы процесса сверх прямого требования задачи, проверь его по частям через [doubt](../doubt/SKILL.md). Если после сравнения остаётся дорогой для переделки спорный вопрос (не закрытый независимым проходом `doubt`), можно запросить проверку предположений у одного независимого read-only субагента без правок и вложенных субагентов.
4. Покажи рекомендацию с причинами, сравнение рассмотренных вариантов и оставшиеся неизвестные — без реализации.

При переходе к подготовке пакета реализации используй [design-plan](../design-plan/SKILL.md). Для продолжения в другой сессии сохрани итог в `.scratch/<тема>/decision.md`.
